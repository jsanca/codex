SUMMARY
-------
Introduced PermissionResolver — the interface that computes effective permissions from role
assignments and role blueprints — and DefaultPermissionResolver, the first in-memory
implementation. The resolver walks the scope hierarchy, enforces the AGENT+SUPER_ADMIN hard
invariant, applies SUPER_ADMIN bypass for non-agent actors, and resolves permission implication
rules from ADR-009. 41 new tests cover all specified behaviours. Test count grew from 104 to
145. Full reactor BUILD SUCCESS.

INTERFACE SHAPE
---------------
PermissionResolver (api, exported):
  boolean hasPermission(Actor actor, PermissionKey permission, ResourceScope target,
                        Collection<RoleAssignment> assignments, Map<RoleKey, Role> roleRegistry)

DefaultPermissionResolver (internal, not exported):
  Implements PermissionResolver. Stateless, final. No persistence, no transport, no mutation.

EVALUATION ORDER
----------------
1. Hard guard — if actor.type == AGENT and any assignment for that actor has SUPER_ADMIN key:
   throw IllegalStateException (system invariant violation, fires before all other logic).
2. SUPER_ADMIN bypass — if actor.type != AGENT and actor has a SUPER_ADMIN assignment whose
   scope covers the target: return true immediately (no role lookup needed).
3. Scope hierarchy walk — starting at target, walk to parent scopes (ContentItemScope →
   ContentTypeScope → SiteScope → GlobalScope), never crossing site boundaries. At each scope,
   find actor's assignments, look up Role in registry, check permissions with implication rules.

SCOPE HIERARCHY
---------------
parentOf() is computed from the child scope's own fields, preserving site identity:
  ContentItemScope(site, type, item) → ContentTypeScope(site, type)
  ContentTypeScope(site, type)       → SiteScope(site)
  SiteScope(site)                    → GlobalScope.INSTANCE
  GlobalScope                        → null (stop)

Site boundary enforcement is structural: the parent walk inherits the same siteKey from the
child scope. An assignment in SiteScope(site-b) can never match a resource in site-a during
a walk rooted at site-a.

SUPER_ADMIN SCOPE COVERAGE
---------------------------
scopeCovers(assignmentScope, targetScope):
  GlobalScope          → covers everything
  SiteScope(site-A)    → covers SiteScope(site-A), ContentTypeScope(site-A, *), ContentItemScope(site-A, *, *)
                         does NOT cover GlobalScope or any scope in site-B
  ContentTypeScope(s,t)→ covers ContentTypeScope(s,t) and ContentItemScope(s,t,*)
  ContentItemScope     → covers only the exact same ContentItemScope

PERMISSION IMPLICATION (ADR-009)
---------------------------------
roleGrantsPermission() applies implication after direct contains() check:
  contentItem.read is also granted if the role contains contentItem.update OR contentItem.publish
  No other implication rules exist.
  contentItem.publish does NOT imply contentItem.update (asymmetric, tested explicitly).

OBSERVATIONS
------------
- The internal package (codex.custos.internal.service) is not exported in module-info.java.
  Maven Surefire 3.5.0 automatically patches the module for tests, consistent with how
  codex-codex handles internal repository and cache subscriber tests.

- SUPER_ADMIN bypass does not require a registry lookup. The bypass fires on the RoleKey alone
  (SUPER_ADMIN_KEY match + scope coverage). This is intentional: the blueprint provides
  introspection value but the bypass semantics are encoded in the evaluator, not the blueprint.

- The resolver is stateless and instantiable without dependencies. Callers are responsible for
  assembling the assignments and registry snapshots. This is sufficient for the current in-memory
  model; a future store-backed resolver can implement the same interface without changing callers.
