POTENTIAL GAPS (worth adding):
  1. Sealed type exhaustiveness: no test verifies exhaustive pattern matching
     over ResourceRef or ResourceScope subtypes (switch/case). This is the
     primary use pattern for these sealed hierarchies.
  2. AccessDecisionService.evaluate(Actor, PermissionKey, ResourceRef) default
     method: no test exercises the 3-arg -> 4-arg delegation. Needs a stub
     PermissionEvaluator to verify the default passes empty() context.
  3. Structural alignment between ResourceRef and ResourceScope: no test
     confirms that e.g. ContentItemResourceRef(s, ct, ci) corresponds to
     ContentItemScope(s, ct, ci) — same keys, same ordering.
  4. Adversarial construction: no test for edge cases like PermissionKey
     with empty string (""), only blank ("   ") and null.
  5. ResourceRef/ResourceScope Cross-site isolation: no test demonstrates
     two SiteScopes with different SiteKeys are not equal.
  6. PermissionEvaluator and AccessDecisionService are interfaces with no
     implementations — no tests possible until Phase 1+.

6. ARCHITECTURE OBSERVATIONS
-----------------------------

POSITIVE:
  - requireGranted() now delegates to new AccessDeniedException(this)
    instead of formatting the message inline. This is the correct pattern:
    callers get the full Denied record, not a parsed string.
  - AccessDeniedException.decision() returns Optional<AccessDecision.Denied>
    — proper use of Optional for valid absence (raw-message constructors).
  - Blank-reason validation added to both Granted and Denied compact
    constructors — good hardening, prevents meaningless decisions.
  - SecurityEvaluationContext.empty() uses a private record singleton
    (EmptyContext) — no exposed mutable state.
  - ResourceRef and ResourceScope are independent sealed hierarchies with
    the same 4-shape structure. This matches ADR-009's explicit
    differentiation between "resource being evaluated" vs "where permission
    is assigned."
  - ContentItemResourceRef carries all 3 keys (siteKey, contentTypeKey,
    contentItemKey) — no cross-site lookup risk. ADR-009 rule satisfied.

MINOR (not blocking):
  1. No internal package exists yet. For Phase 0 this is acceptable
     (only interfaces and model types). When PermissionEvaluator or
     MemoryGrantStore implementations are added, they should go into
     codex.custos.internal.
  2. Identity naming in codex-codex: both SiteKey and SiteId exist.
     Custos uses *Key variants consistently. An unfamiliar agent might
     use SiteId by mistake. Worth documenting that Custos uses *Key types.
  3. The AccessDecision interface exposes isGranted() boolean alongside
     the sealed hierarchy. ADR-009 recommends preferring pattern matching.
     The JavaDoc echoes this — no action needed, but worth noting this is
     a potential anti-pattern if callers use isGranted() bypassing the
     sealed switch pattern.

NO CHANGE REQUIRED. The hardening diff is clean and ready.
